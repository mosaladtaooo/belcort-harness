# BELCORT Harness Engine

You operate within the BELCORT Harness Engine — a Planner → Generator → Evaluator pipeline inspired by Anthropic's harness engineering research. This snippet is deliberately small: activation logic and red-flag rules only. Everything else (pipeline flow, subagent dispatch blocks, file ownership contract, TDD protocol, MCP setup, manifest schema) lives in the harness skill — loaded only when the skill is active.

## Three Agents, Three Jobs

| Agent | Job | Context |
|-------|-----|---------|
| **Planner** | Expand prompt → PRD + high-level tech direction + draft contract | Fresh subagent |
| **Generator** | Negotiate mode: propose HOW. Build mode: implement with TDD | Fresh subagent per mode |
| **Evaluator** | Review-proposal mode: check plan. Evaluate mode: test running app, grade | Fresh subagent (MUST be separate from Generator) |

The Evaluator MUST NEVER share context with the Generator — that's the core GAN insight from the Anthropic research.

## The 1% Rule (adapted from Superpowers)

**If there is even a 1% chance the harness should be active, check for it.** Not optional. Not negotiable. You cannot rationalize your way out of this.

### Session start behavior
The SessionStart hook fires automatically and injects harness state. You don't need to do anything — the hook handles detection. Subagent dispatches pass `CLAUDE_SUBAGENT=1` so the hook skips them (prevents state leakage into fresh subagent contexts).

### When `.harness/manifest.yaml` exists
- You MUST read it before doing anything else
- If `state.phase` is not "complete": tell the user the harness is active and offer `/harness:resume`
- Do NOT start coding, do NOT answer technical questions about the project, until you've acknowledged the harness state
- The harness state is your source of truth — not your memory of previous conversations

### When no harness exists but the user describes building something
Trigger words: "build", "create", "implement", "make an app", "develop", "set up a project", "new feature" (when substantial, not a one-liner fix).

If you detect these AND the request involves multiple components, a full feature, or anything that would take more than 15 minutes to build well:
→ Suggest: "This looks like it would benefit from the harness pipeline. Want me to run `/harness:sprint`?"

Do NOT suggest the harness for:
- Quick questions ("how do I X?")
- Single-line fixes ("fix this typo")
- Conversational requests ("explain how React hooks work")
- Tasks the user is clearly doing manually and wants help with

### Red flags (you're about to skip the harness when you shouldn't)
- "I know how to build this, I'll just start coding" → STOP. That's exactly when the harness helps most.
- "This is simple, I don't need planning" → Check: is it actually < 15 min, or are you underestimating?
- "The user didn't ask for the harness" → You don't need them to ask. Suggest it if it fits.

## Commands

| Command | What it does |
|---------|-------------|
| `/harness:sprint "<prompt>"` | Full loop: plan → analyze → [human gate] → negotiate → build → evaluate → tuning → retrospect → merge |
| `/harness:quick "<prompt>"` | Skip planning. Minimal contract. Build → single QA pass |
| `/harness:resume` | Read manifest.yaml + changelog, continue from last phase (handles mid-build recovery) |
| `/harness:validate` | Run 16-point quality audit on existing spec files |
| `/harness:edit "<change>"` | Targeted spec modification with downstream reference updates |
| `/harness:analyze` | Cross-artifact consistency check (PRD vs architecture vs contract) |
| `/harness:negotiate` | Generator ↔ Evaluator contract negotiation before build |
| `/harness:retrospective` | Post-merge drift analysis — sync spec with what was actually built |
| `/harness:tune-evaluator` | Review divergence patterns and propose calibration improvements |
| `/harness:audit` | Verification debt scan — deferred issues, stale known-issues |

## Rules

1. If a `.harness/` exists, read `manifest.yaml` before doing anything.
2. Evaluator is ALWAYS a separate subagent — never self-evaluate in the same context.
3. Every technical decision must align with `constitution.md`.
4. Agents communicate via `.harness/` files, never via shared context. **The orchestrator (this session) does NOT edit spec files directly — dispatch a subagent in the right mode instead.** The whole point of the harness is to keep the orchestrator's chat context out of those files.
5. When uncertain, ask the human ONE focused question.
6. Planner does NOT specify files, components, data models, or API paths — those are negotiated between Generator and Evaluator before building.
