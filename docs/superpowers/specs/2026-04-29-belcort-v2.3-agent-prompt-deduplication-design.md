# BELCORT Harness — v2.3 Agent-Prompt Deduplication (Design Spec)

**Date**: 2026-04-29
**Author**: BELCORT (tao@belcort.com)
**Target model**: `claude-opus-4-7[1m]` (1M context variant — same as v2.2)
**Refactor scope**: post-v2.2 agent-prompt deduplication + bash de-prescription. Three changes, one PR, ~50-55 LoC net reduction across two agent files.
**Predecessors**:
- `2026-04-21-belcort-v2-minimalist-refactor-design.md` (v2.0 minimalist refactor — established the ruler)
- `2026-04-28-belcort-audit-and-refine-design.md` (v2.2 stale-assumption pruning — same ruler applied to four post-v2.0 targets)

This spec extends the same logic — *"every component encodes an assumption that may go stale as models improve"* — to three patterns surfaced on a follow-up audit of `agents/generator.md` (526 LoC) and `agents/evaluator.md` (662 LoC).

---

## 1. Context & Motivation

After v2.2 shipped, the framework owner asked three follow-up questions during a re-audit pass:

1. *"Generator execute develop — is it good enough?"*
2. *"Evaluator approach — is it still bloated?"*
3. *"Does bash and command line still need to be included in prompts, or just natural language?"*

A fact-based read of the three agent files (with `file:line` citations) surfaced three concrete patterns that fail the v2.0/v2.2 ruler:

1. **Generator has the same TDD/reward-hacking discipline stated in three overlapping sections** — `RED FLAGS` table (`generator.md:144-167`), `REWARD-HACKING — FORBIDDEN` (`generator.md:507-525`), and `ANTI-PATTERNS` (`generator.md:498-505`). Eight of the nine bullets in ANTI-PATTERNS appear verbatim or near-verbatim in the RED FLAGS table; four of the five NEVER rules in REWARD-HACKING — FORBIDDEN do too. Single-source-of-truth violation.

2. **Evaluator has the exact same "READ THIS CAREFULLY" leniency-bias warning twice** — once at agent-level (`evaluator.md:54-55`), once at mode-level (`evaluator.md:261-262`), with the same Anthropic quote and near-identical wording. Single-source-of-truth violation.

3. **Evaluator over-prescribes bash** — 4 bash blocks (`evaluator.md:348-381` Step 1 setup, `evaluator.md:446-459` Step 3 code-quality, `evaluator.md:469-478` Step 4 test-suite, `evaluator.md:494-514` Step 4.5 reward-hacking scan). Three of these are generic operations Claude infers from natural-language intent (read these files, scan for these patterns, run the project's test command). One is genuinely load-bearing — the reward-hacking scan's regex patterns ARE the spec, not boilerplate. The other three encode the assumption *"the agent needs the literal command sequence"* which has staled on Opus 4.7.

For contrast, `planner.md:76` already explicitly states *"You do NOT have Bash. Planning is a read-and-write activity, not a command-execution activity."* — Planner has 0 bash blocks. The framework already trusts the model in one place; v2.3 brings the other two agents into alignment.

### Anti-goal

Not a redesign. Not new features. Not a paradigm shift. Same minimalist instinct as v2.0/v2.2, applied to two more accreted patterns. The Generator and Evaluator pipelines are structurally sound — only the prompt content is being trimmed.

## 2. The Ruler

Same ruler as v2.0/v2.2; restated only the lines that bind v2.3:

1. *"Find the simplest solution possible, and only increase complexity when needed."* — Rajasekaran 2026 (single-source-of-truth violations are unnecessary complexity)
2. *"Every component in a harness encodes an assumption… those assumptions are worth stress testing… they can quickly go stale as models improve."* — Rajasekaran 2026 (the bash-in-prompt assumption)
3. **Trust the model's tool use.** Carryover user constraint from v2.2. The model knows how to read files, grep code, run `npx vitest run`. Telling it the literal command is over-prescription that increases prompt token cost and reduces flexibility.

**User-stated constraints (this round):**

4. *"Do it all, follow your recommendation queue."* — single PR, scope A+B+C, no D (ESLint context unavailable; D deferred).
5. No user-facing command surface change.

## 3. Goals & Non-goals

### Goals

- G1. Eliminate the three-section TDD/reward-hacking redundancy in `generator.md`. One source of truth (the RED FLAGS table) + one short cross-referencing reward-hacking section + zero standalone ANTI-PATTERNS section.
- G2. Eliminate the duplicate "READ THIS CAREFULLY" warning in `evaluator.md`. Keep only the EVALUATE-mode-specific copy.
- G3. Convert generic bash blocks in `evaluator.md` to natural-language intent statements. Keep literal bash only where the specific command/regex IS the spec.

### Non-goals

- N1. **No change to `planner.md`** — already correct on bash philosophy (`planner.md:76`).
- N2. **No change to mode routing, pause protocol, recovery procedure, or file ownership** — all unchanged from v2.2.
- N3. **No change to the Step 4.5 reward-hacking scan in `evaluator.md`** — its bash regex patterns are domain-specific spec (commit-message tag detection, test-file-naming patterns, `.skip`/`xit` marker scans). Replacing with natural language would lose specificity Claude can't infer.
- N4. **No change to `RED FLAGS` table format in `generator.md`** — Anthropic's adversarial 1%-rule pattern. Tables of rationalizations + counters are load-bearing, not bloat.
- N5. **No version-incompatible state changes** — v2.2 manifests, contracts, and reports remain valid under v2.3.
- N6. **ESLint 9 config-resolution diagnostic (the user's side question)** — string is not in the BELCORT repo (verified via grep). Deferred until source is identified.

## 4. Concrete changes

Three changes, two files. Each shows current state, target state, and rationale.

### Change A — Generator dedup (`plugins/harness/agents/generator.md`)

#### A.1 Drop `## ANTI-PATTERNS` section

**Current** (`generator.md:498-505`, 7 lines):

```markdown
## ANTI-PATTERNS

- **Test-after**: Writing code first, tests second. The test will be biased toward your implementation.
- **Mega-commits**: 15 files in one commit. Break it up.
- **Stubbing**: "TODO: implement later." If it's in the contract, build it now.
- **Guessing APIs**: "I think the method is called `.findOne()`..." — USE CONTEXT7.
- **Ignoring errors**: Empty catch blocks, swallowed exceptions, no error UI states.
- **Skipping self-eval**: Handing off without checking your own work. The Evaluator should find SUBTLE issues, not obvious ones you could have caught.
```

**Target**: section deleted in entirety.

**Rationale**: Every bullet is already present in the RED FLAGS table at `generator.md:144-167`:

| ANTI-PATTERNS bullet | RED FLAGS row that subsumes it |
|---|---|
| Test-after | "I'll write the code first, the test after — I already know what the test will look like" |
| Mega-commits | "One big commit is cleaner than five small ones" |
| Stubbing | "I'll stub this function and mark the FR done" |
| Guessing APIs | "I remember this API, skipping Context7" |
| Skipping self-eval | "I'll self-evaluate generously — it's been a long sprint" |

The "Ignoring errors" bullet is the only one without a direct RED FLAGS analogue, but it's covered by the constitution check + Phase 3 self-eval checklist (`generator.md:436` — "Error handling at all boundaries"). No information loss.

#### A.2 Compress `## REWARD-HACKING — FORBIDDEN` section

**Current** (`generator.md:507-525`, 18 lines): 5 NEVER rules + 1 corrective procedure.

**Target** (~6 lines):

```markdown
## REWARD-HACKING — FORBIDDEN

The RED FLAGS table above covers the rationalizations you'll try (test deletion, weakening assertions, `.skip`, stubbing). Treat each as an absolute prohibition during BUILD mode, not a heuristic.

**One rule the table doesn't restate**: NEVER modify a test in the same commit as the code it tests, unless the commit is clearly an initial TDD-RED test. Editing a test + the implementation simultaneously hides whether the test was weakened to fit broken code; the Evaluator's git-archaeology scan in EVALUATE mode flags this pattern as CRITICAL.

If a test genuinely needs to go because the spec changed: stop the build (`/harness:rewind building`), update the spec via `/harness:amend`, restart. The test deletion appears in a commit whose message references the ADR. This is slower; that's the point.
```

**Rationale**: Of the 5 NEVER rules, 4 (delete test / weaken assertions / skip-or-xit / no-op assertions) are restatements of RED FLAGS rows. The 5th (modify test+code in same commit) is genuinely additional. Cross-referencing the table preserves the discipline without duplicating it; the corrective procedure stays because it's actionable guidance not in the table.

**Net A save**: **~20 lines** (7-line ANTI-PATTERNS deleted + 19-line REWARD-HACKING compressed to ~6 lines = 7 + 13 = 20).

### Change B — Evaluator de-bash (`plugins/harness/agents/evaluator.md`)

Replace three generic bash blocks with natural-language intent statements. Keep the reward-hacking scan literal.

#### B.1 Step 1 Setup — replace bash with NL

**Current** (`evaluator.md:348-381`, 33 lines): 11 commands wrapping `cat`/`grep`/`awk`/`bash` — feature-name extraction, calibration reads, marker check, build artifact reads, criteria/constitution reads, app start.

**Target** (~16 lines):

```markdown
### Step 1: Setup (2 minutes)

The current feature folder name lives in `.harness/manifest.yaml` under `state.current_feature`.

**Calibrate first** — read these BEFORE anything you'll grade, so the Generator's framing doesn't anchor your scoring scale:
- `.harness/evaluator/examples.md` (mandatory)
- `.harness/spec/evaluator-notes.md` (if present)

**Verify the contract is final** — `.harness/features/{feature}/contract.md` must contain a `**Negotiated**:` marker at the top. If absent, the contract is still a draft; file a CRITICAL "evaluation cannot proceed against draft contract" finding and stop. The negotiation-gate exists for a reason.

**Read the build artifacts** in this order: `implementation-report.md` (Generator's handoff), `contract.md` (final negotiated), `proposal.md` (committed HOW), `review.md` (your own pre-build review notes — the WHY behind certain ACs).

**Read grading + standards**: `criteria.md` (rubric, global), `constitution.md` (code standards).

**Start the app** via `bash .harness/init.sh`. If init.sh fails, file a CRITICAL "app does not start" finding and stop — you cannot evaluate a non-running app.
```

**Rationale**: The bash version encodes the SAME intent (calibrate first, verify marker, read in order, start app) but commits to a literal command sequence that's brittle (the YAML extraction `awk '{print $2}' | tr -d '"'` breaks if YAML format shifts; the orchestrator already passes feature name in dispatch context, making the extraction redundant). Natural language is shorter, more flexible, and states the gating failures explicitly (which the bash version had to wrap in `||` echo statements).

#### B.2 Step 3 Code Quality Review — replace bash with NL

**Current** (`evaluator.md:446-459`, 13 lines): `find` for file lengths, `grep` for `console.log` and `: any`, `npx eslint`.

**Target** (~6 lines):

```markdown
### Step 3: Code Quality Review

Read the source files and check against the constitution. Use Bash with whatever scan commands fit the stack:
- File-length violations against constitution's max (typically 300 lines)
- Forbidden patterns per constitution (`console.log`, `: any`, `eval(`, etc.)
- Project's lint script (`npm run lint`, `pnpm lint`, `npx eslint src/`, `cargo clippy` — check `package.json`/`pyproject.toml`/etc.)

Beyond grep-able patterns, manually review: function lengths (flag any >50 lines unless the constitution explicitly allows), error handling at boundaries (API calls, user input), import hygiene (unused imports, circular deps), naming conventions per constitution.
```

**Rationale**: The bash version assumes a TypeScript project (`*.ts`, `*.tsx`, `npx eslint`). The natural-language version generalizes across stacks while preserving the same scan intent. Claude with Read + Bash tools doesn't need scripted commands for "find files over N lines" or "grep for `: any`" — both are obvious from the constitution's rules.

#### B.3 Step 4 Test Suite Analysis — replace bash with NL

**Current** (`evaluator.md:469-478`, 9 lines): `npx vitest run`, `npx playwright test`, `git log --oneline --name-only | head -60`.

**Target** (~5 lines):

```markdown
### Step 4: Test Suite Analysis

Run the project's full test suite (typically `npm test` / `npx vitest run` — check `package.json` test script) and any E2E suite (`npx playwright test` if Playwright is configured).

Cross-check the git log for TDD evidence — test files should appear in commits BEFORE the implementation files for the same FR. `git log --oneline --name-only | head -60` is one way; the pattern matters more than the exact command.

Evaluate: do tests pass, do they assert real behavior (not just "renders without crash"), is there TDD evidence in commit ordering, are critical paths covered, are tests deterministic?
```

**Rationale**: Same as B.2 — generalizes across stacks, preserves intent. The git log command is mentioned but not pinned, signaling that the pattern (test-before-implementation in commit history) is what matters.

#### B.4 Step 4.5 Reward-hacking scan — UNCHANGED

`evaluator.md:494-514` (21 lines, 6 bash sub-blocks A-F) stays literal. Each regex captures domain-specific spec:
- Block A: test file conventions (`__tests__/`, `/tests?/`, `playwright.config`)
- Block B: same-commit test+implementation pattern
- Block C: skip/xit/xdescribe markers
- Block D: trivial truthiness assertions
- Block E: commit-message keywords suggesting test weakening
- Block F: explicit no-op assertions

Replacing these with natural language ("look for skipped tests") would lose the specific patterns Claude wouldn't infer. They ARE the spec.

**Net B save**: 17 (Step 1) + 7 (Step 3) + 4 (Step 4) = **~28 lines**.

### Change C — Evaluator duplicate-warning fix (`plugins/harness/agents/evaluator.md`)

**Current**: same "READ THIS CAREFULLY" leniency warning at two locations.

| Location | Lines | Wording |
|---|---|---|
| Agent-level intro | `evaluator.md:54-55` | "This prompt is specifically designed to counteract that bias." |
| EVALUATE mode | `evaluator.md:261-262` | "This mode's prompt is specifically designed to counteract that bias." |

Same Anthropic quote, near-identical wording, near-identical instruction.

**Target**: delete `evaluator.md:54-55`. Keep `evaluator.md:261-262`.

**Rationale**:
- REVIEW-PROPOSAL mode (lines 60-156) has a different failure mode — *rubber-stamping*, addressed by the explicit "Rubber-stamping" anti-pattern at `evaluator.md:151`.
- REVALIDATE mode (lines 159-249) is binary PASS/FAIL, leniency bias doesn't apply numerically; covered by "Lenient pass-by-default" anti-pattern at `evaluator.md:246`.
- Only EVALUATE mode involves numeric grading where the documented Anthropic leniency bias is operative.

The agent-level copy fires before mode routing, so it primes ALL three modes — including the two where it's wrong. The mode-level copy (line 261) anchors the anti-leniency protocol that immediately follows in EVALUATE mode (lines 600+). One copy, scoped to where it's relevant.

**Net C save**: ~3 lines.

## 5. Trade-offs

### What we gain

- **~50-55 LoC reduction** across `generator.md` (-20 from Change A) and `evaluator.md` (-31 from Changes B + C). Smaller agent prompts = lower per-dispatch token cost = more headroom in the 1M context window.
- **Single source of truth** for TDD/reward-hacking discipline (RED FLAGS table is canonical) and for leniency-bias warning (EVALUATE-mode copy is canonical).
- **Stack flexibility** in evaluator's Steps 3 and 4 — the natural-language versions work for TS/JS/Python/Rust/Go projects; the bash versions assumed `npx eslint` and `npx vitest`.
- **Alignment with v2.2's "trust the model" stance** — same logic that drove dropping the hard Planner size gate, applied to the bash-in-prompt assumption. If v2.2 shipped, v2.3 follows.

### What we give up

- **Verbatim copy-pasteability of bash commands.** The previous Step 1 setup was paste-able into a terminal as-is. Post-v2.3, Claude has to translate intent to commands. **Mitigation**: Claude is the user of these prompts, not a human. Claude does this translation reliably. The "human reads agent prompt and pastes into terminal" workflow is not a real workflow — these are subagent dispatch prompts, not runbooks.
- **Symmetry of "READ THIS CAREFULLY" warnings across modes.** Pre-v2.3, every mode saw the leniency warning. Post-v2.3, only EVALUATE mode does. **Mitigation**: REVIEW-PROPOSAL and REVALIDATE have their own anti-pattern callouts addressing their specific failure modes. The asymmetry is correct, not regression.

### What we explicitly didn't do

- **N1. Touch `planner.md`.** Already correct on bash philosophy.
- **N2. Touch the RED FLAGS table itself.** Anthropic's adversarial 1%-rule format is load-bearing.
- **N3. Touch the reward-hacking scan bash.** Patterns ARE the spec.
- **N4. Touch mode routing, pause protocol, recovery procedures, file ownership, or any v2.2-introduced contract.** All v2.2 invariants must continue to pass post-v2.3.
- **N5. Address the user's ESLint 9 / config-resolution / constitution-checks.sh diagnostic.** Not in repo (grep verified). Deferred.

## 8. Implementation method

Subagent-Driven Development (`superpowers:subagent-driven-development`):

- Group 1: Generator dedup (Change A) — 1 implementer subagent, 1 spec reviewer, 1 code-quality reviewer
- Group 2: Evaluator de-bash (Change B.1, B.2, B.3) — 1 implementer subagent, 2 reviewers
- Group 3: Evaluator dup-warning fix (Change C) — inline edit (3 lines, mechanical)
- Group 4: Versioning + CHANGELOG + ADR — inline edit
- Group 5: Verification grep run

Per-group review surfaces real issues to fix inline (precedent: v2.2 implementation surfaced 5 stale step-headings in Group D and 5 secondary `/harness:negotiate` refs in Group E that the spec didn't enumerate but which had to be fixed before merge).
